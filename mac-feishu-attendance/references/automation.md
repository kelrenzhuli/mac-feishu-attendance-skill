# 定时激活与恢复

## 先确定行为

- 用户需要的是提醒、仅检查按钮，还是允许实际产生考勤记录；只有用户明确要求的动作才执行。登录验证码由用户输入。
- 获取用户的上下班时间、时区、具体班次以及请假、调班、加班和休息日规则；不要把某台机器的星期和时刻当作通用规则。按用户要求校验本人发起的相关审批，来源不完整或无法读取时跳过。
- 打卡依赖本人实际到岗的制度：Mac 留在办公室并连接 Wi-Fi，不能证明本人在场。对用户说明这一事实，由用户决定合适的触发方式。

## 可复现的判断

尝试一次之前，核对：Mac 实际接入点、安卓联网、飞书账号和组织、页面日期和时钟、当天班次、对应上下班卡未打、Wi-Fi 在考勤范围内、相关审批和用户指定时间。两次读取之间状态变化、登录失效、网络不符或页面无法识别时跳过。出现虚拟定位、模拟位置、疑似作弊或设备风险提示时暂停定时激活，使用真实设备或管理员允许的方式核对考勤。日期和时段采用目标时区，开机补跑不能在错过的时间盲目补打。

`scripts/page_check.py` 仅覆盖其中的页面条件；它不验证实际网络、审批、设备真实性或服务器打卡记录，也不点击按钮。获取 Android 无障碍树时注意 Avo 的应用可能在非默认显示屏：必须验证当前前台 Activity 和 XML 内容属于正确的飞书考勤页。临时 XML 应放在私有位置并及时删除，不要上传日志、截图或用户配置。

如果方案使用飞书极速打卡，只在用户指定的有效时段、完成前置检查后重新激活；该动作本身可能立即提交考勤。避免退出正在进行的重要操作，每一时段最多一次。之后查看飞书机器人消息或当天打卡记录，只有实际记录与时段吻合才能称为成功；否则记录“已激活，结果未确认”。

如果确认账号、当天班次或申请的唯一方式是打开飞书，而打开可能立即触发极速打卡，那么“打开后再检查”已经太晚。应先使用独立、可靠的数据来源确认条件；做不到时跳过，不能把旧页面或固定星期时间当成当天班次。

## 本次实践采用的组件

1. 用户登录后的守护任务检查 Avo 状态、外置盘和真实 Wi-Fi；仅在所需时段启动或恢复模拟器，并使用锁避免重复运行。
2. 定时任务在指定上下班时段核查网络、页面与本人发起的相关审批；出现未知、冲突、已打卡或特殊班次时跳过。
3. 仅在允许的窗口内重新激活飞书，由飞书原生极速打卡决定是否记录；不以模拟点击、按钮变亮或任务退出成功作为打卡成功的证据。
4. 从飞书记录或机器人结果核对，有结果才标记成功。Mac 登录后的模拟器启动与 Wi-Fi 恢复是另一项任务，不等同于开机立即打开飞书。

这些是对一次本机实验的设计记录，并非本仓库中可直接启用的完整调度器。当前页面检查只适配已观察到的一种布局；新版本、不同考勤组和不完整审批数据都需要重新验证。

## macOS / Avo 的持续运行

- Avo 可在闲置时暂停安卓；通过 Avo 的 Performance 设置或其官方 CLI 调整，而不是改系统映像。按用户需求选择是否运行 `caffeinate -i`，说明系统闲置时不会自动睡眠。
- 用户会话中的 `~/Library/LaunchAgents` 可在登录后启动守护程序、按时间调度；退出登录、关机或外置盘没挂载会影响运行。启动任务应等待并校验已有外置数据，不能自动创建替代数据盘。
- 开机先启动模拟器并不意味着飞书也打开。**飞书一旦打开就可能立即极速打卡**：若启动前无法实时确认账号和当天班次，不能声称开机后会安全完成全自动打卡。仅在满足用户已选时刻与规则时启动；否则跳过或由用户处理。
- 检查登录后能否恢复权限、网络、飞书和考勤页。模拟器重启成功不等于 Mac 整机重启成功；除非实际测试过，不要声称已经验证。
- 日志记录时间、结果和可理解的失败原因，不保存原始无障碍树、账号信息、Wi-Fi 标识或凭据。提供停止、恢复和检查运行状态的方法。
