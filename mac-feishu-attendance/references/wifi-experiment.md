# Avo Wi-Fi 实验的范围

## 已观察到的事实

Avo 的安卓访客使用虚拟无线接口与宿主机网络通信；Mac 连接到公司 Wi-Fi 并不意味着 Android 会直接报告相同的 SSID/BSSID。一次 Avo 1.1.0、Android 16 build 15581820 的实验中，Android 最初显示 `VirtWifi`，飞书未把它识别为指定公司 Wi-Fi。

在用户允许且 Mac **确实连接指定接入点**的前提下，实验用 macOS CoreWLAN 读取当前 SSID/BSSID，并为该 Android 构建生成临时 `virt_wifi` 驱动；访客报告的标识与宿主机接入点一致。实际数据流仍经过模拟器的网络，不是物理 Wi-Fi 桥接，也不证明通过服务端风控。

## 受限的离线补丁

`scripts/patch_wifi_module.py` 只支持 SHA-256 为 `51e82f889a7c4037099ac7f23c92322a36b31e953894ab4bf9c2967833833daa` 的原始 ARM64 模块，以及 UTF-8 编码后**恰好 9 字节**的 SSID。它核对特定 ELF 布局与指令，输入必须来自最近更新的、获得定位授权的本机 Wi-Fi 状态文件；其他构建或长度一律拒绝。该补丁中的连接检查只比较 SSID 的前 8 个字节和总长度，不能作为接入点身份验证；仍须由宿主机守护程序校验完整 SSID 和 BSSID。它只在用户指定位置生成一个新文件，不安装或加载模块。不要把 `.ko`、Wi-Fi 状态文件或标识提交到 GitHub。

样例流程（路径由用户本机配置，先阅读脚本帮助）：

1. 检查 Avo 的版本、Android 构建、目标虚拟设备和原始模块散列。只在用户授权后读取本机 Wi-Fi，macOS 可能要求定位权限；不获取密码。
2. 使用 `scripts/AvoWifiProbe.swift` 构建已签名的本机辅助程序，按用户批准请求权限，并以私有文件持续记录当前 Wi-Fi 状态。构建及授权方式取决于本机环境。
3. 从已验证的 Android 镜像取得原始模块，并运行离线补丁脚本生成临时副本。仅成功生成不代表适配成功。
4. 实际加载需要额外的、经测试的宿主机守护程序和 Android 看门狗：宿主机状态过期或接入点不匹配时立即停用同步、恢复原模块；守护程序停止心跳时访客侧关闭 Wi-Fi。本仓库**未提供完整的通用加载/守护程序**，不要自行把补丁加载当成现成的一键方案。
5. 在不提交考勤的情况下检查安卓报告、飞书范围、切换/断网/守护程序故障及重启后的恢复。MAC 型 Wi-Fi 与公网 IP 型考勤、拍照/人脸规则可能不同，以飞书和管理员规则为准。

匹配页面上的公司 Wi-Fi 不等于真人在场、真实接入点桥接或成功打卡。必须与实际宿主机连接绑定；不把失联后的旧 SSID/BSSID 当成有效证据，也不绕过考勤规则或风控。
